# Grafana dashboard review

**23 November 2026 · HPC Demo · revision `312edc8`**

**The dashboards need revision before students rely on the filtered percentages and run-to-run deltas.** The clearest example came from selecting the search route. Search runs entirely inside the API, yet Dependency Health showed that downstream calls accounted for **182.79%** of its traffic. The whole-API share at the same timestamp was **32.50%**.

I inspected all seven provisioned dashboards and matched the titles and queries of all 94 panels, including four log panels and six text panels or rows, to the checkout. I rendered each dashboard at desktop width, checked Load Test Correlation at 430 px, and exercised selected filters and a dashboard link. I used the saved baseline, degraded, smoke, and overlapping breakpoint runs from 03:03:30–03:08:45 UTC on 23 November. All measurements below come from that window. Numerical and interaction checks were sampled.

## Prioritized opportunities

| Priority | Finding and classroom consequence | Proposed change and acceptance check |
|---|---|---|
| 1 | **Dependency share can exceed 100%.** At 03:07:50 UTC, selecting `/api/search` narrowed the API denominator while the numerator still counted every outbound call. [Dependency Health](observability/grafana/dashboards/dependency-health.json#L129) | Define this panel as “Share of all API requests that called the dependency” and keep the whole-API denominator fixed. If a route-specific share is wanted, count dependency-backed requests within that same route. The all-API figure should read 32.50% at this timestamp, and a true search-only share should read 0%. |
| 1 | **The comparison hides the biggest workload change.** The degraded operation went from zero to 3,220 of 10,493 requests (**+30.69 percentage points**). Slow went from 1,020 of 19,881 requests to zero (**−5.13 points**). The delta panel displayed only fast, search, and dependency because those occurred in both runs. Its target panel also showed only the baseline mix. [Run Comparison](observability/grafana/dashboards/run-comparison.json#L1163) | Compare the union of operations. Fill an absent operation with zero only after confirming its run had traffic. Show each run’s target next to its actual share. The saved comparison should show five operations, including both changes above. |
| 1 | **Two valid runs produce an impossible target.** Selecting baseline and degraded together gives targets of 60% fast, 20% search, 15% dependency, 5% slow, and 30% degraded. The panel takes the largest target per operation and totals **130%**. The drift panel then compares real traffic with that mix. [Load Test Correlation](observability/grafana/dashboards/load-test-correlation.json#L1073) | For this teaching lab, enable target and drift panels when one run is selected. When several are selected, give students a one-line prompt or show each run separately. Every displayed run target should total 100%. |
| 1 | **Filters can imply scope they do not apply.** All eight Endpoint Comparison measurement panels ignore the run ID, workload profile, and operation selectors directly. The four workload selectors on Infrastructure Overview do not restrict any of its 14 queries. Following the failed candidate from Run Comparison to Endpoint Comparison preserved the time range but opened with **Test Run ID = All**. Root Cause Drilldown has no incoming dashboard link or run selector. [Endpoint Comparison](observability/grafana/dashboards/endpoint-comparison.json) · [Infrastructure Overview](observability/grafana/dashboards/infrastructure-overview.json) · [Root Cause Drilldown](observability/grafana/dashboards/root-cause-drilldown.json#L153) | Provide separate **Inspect base** and **Inspect candidate** links that carry the chosen ID and run time window. Label service metrics “all API traffic in this interval” and infrastructure charts “whole host.” Carry the ID into both Loki queries. Overlapping runs should remain distinguishable when students open logs and follow a trace. |
| 1 | **Adjacent workload charts answer different questions.** At 03:07:50 UTC, fast handled 44.19 of 76.95 report requests/s (**57.42%**). Selecting fast alone makes Endpoint Comparison’s percentage-stacked chart fill to **100%**. Load Test Correlation has the same issue on the API side, next to a k6 chart that preserves the whole-workload denominator. [Endpoint share](observability/grafana/dashboards/endpoint-comparison.json#L233) · [API share](observability/grafana/dashboards/load-test-correlation.json#L622) | Calculate shares explicitly before filtering the displayed series, use normal stacking, and name the denominator. Selecting fast should leave its whole-workload share at 57.42% in the saved example. |
| 1 | **Some charts give measurements the wrong units, or turn healthy traffic into a gap.** Runtime Pressure puts **125,218,816 bytes** of memory and **2.06 ms** of event-loop lag on one bytes axis. Dependency Service Health puts latency and a 5xx fraction on one milliseconds axis. At 03:05:45 UTC the API served **166 requests/s**, yet its 5xx chart returned no series. [System Overview](observability/grafana/dashboards/system-overview.json#L186) · [Dependency Service Health](observability/grafana/dashboards/dependency-health.json#L340) | Split unlike quantities or give them clearly labeled axes. Return 0% errors for a group with observed traffic and no failures. Keep a genuinely missing traffic denominator empty. The baseline should visibly read “0% errors” and the lag line should be readable in milliseconds. |
| 2 | **Headline throughput and concurrency need more precise definitions.** Run Comparison showed **159.07 vs 83.89 requests/s** for baseline and degraded. k6 measured **165.40 vs 87.09**. The cards infer elapsed time from sample count and a fixed five-second interval. The ten-request smoke run returned no rate. At 03:07:04, fresh samples from three overlapping runs summed to **24 virtual users**, while “Active VUs” showed **20**, the largest individual value in the window. [Request rate](observability/grafana/dashboards/run-comparison.json#L96) · [Active VUs](observability/grafana/dashboards/load-test-correlation.json#L88) | Persist actual elapsed run time and divide the final request count by it. Rename the VU card **Peak VUs in one run** if that is the lesson, or explicitly compute concurrent VUs with run-end handling. Test the short smoke case and overlapping runs. |
| 2 | **The comparison is hard to read on a shared screen.** At 1440 px, several of the 18 comparison-card headings were truncated. A failed breakpoint’s **100% error rate rendered green**. On a 430 px view of Load Test Correlation, eleven selectors and the metadata panel put the first KPI about **605 px** from the top. [Comparison cards](observability/grafana/dashboards/run-comparison.json) · [Correlation controls](observability/grafana/dashboards/load-test-correlation.json) | Use one comparison table with Metric, Base, Candidate, and Change. Label differences between rates in percentage points. Keep colors neutral for measurements and reserve pass/fail colors for the selected scenario’s actual thresholds. Lead the correlation dashboard with run selection and put secondary selectors and expanded run IDs below the first evidence. |

## Recommended delivery order

1. **Fix the arithmetic.** Add regression fixtures for the search-route denominator, an operation present in just one run, a multi-run target, and a filtered API share. The existing dashboard-query test harness can exercise these cases. [Dashboard query tests](tests/dashboard-queries.test.mjs)
2. **Make the investigation reproducible.** Give students a candidate-to-log path they can follow while two runs overlap. A single selected run should lead from its client measurements to the appropriate time window, then to that run’s API log, downstream log, and trace.
3. **Improve the projector view.** Put the run comparison and its verdict in the first screen. Add run-start, run-end, and breakpoint-stage annotations so students can connect a latency change to the load being applied.
